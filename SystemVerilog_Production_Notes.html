SystemVerilog for RTL, Verification, Interviews, and Production

A practical guide built from the supplied stripped-down language reference

This guide focuses on what code means, whether it synthesizes, and what hardware it can become. It also adds the production topics that are essential but absent from the supplied extract: enums, packed structs and unions, interfaces and modports, unique/priority, packages, assertions, and a complete worked RTL example.

The rule that prevents most confusion: SystemVerilog is both a hardware-description language and a verification programming language. Some constructs describe gates and storage. Others create simulator-only software. Always ask, “Does this statement describe a fixed amount of hardware?”

How to use this guide

  • For interviews: learn the “Interview leverage” and “Trap” callouts and be able to sketch the hardware beside each RTL example.
  • For RTL work: concentrate on Chapters 1–9 and the worked design in Chapter 14.
  • For verification work: add Chapters 10–13.
  • For production: run lint, simulation, assertions, synthesis, and equivalence checks. Legal syntax is not automatically good RTL.

Legend

  • RTL / synthesizable: normally maps to fixed hardware in FPGA/ASIC tools.
  • Testbench only: runs in a simulator; it does not become gates.
  • Tool-dependent: supported by many tools, but verify your synthesis and style guide.

1. The mental model: code becomes hardware

SystemVerilog RTL is not software executed one statement at a time. An always_comb block describes logic that exists continuously; an always_ff block describes state that changes on a clock edge.

What common RTL becomes

RTL pattern Typical inferred hardware
Boolean/arithmetic expression gates, carry chain, DSP block, or optimized network
if / case in combinational logic multiplexer, decoder, comparator network
assignment in always_ff @(posedge clk) D flip-flop(s)
conditional assignment in always_ff flip-flop with enable, usually implemented through a data-input mux
incomplete assignment in combinational logic latch (usually accidental)
fixed-size array with recognized access pattern registers, LUT RAM, block RAM, or SRAM macro
for loop with static bounds replicated/unrolled hardware
class, mailbox, semaphore, random constraint simulator objects and algorithms; no hardware

Synthesis is not guaranteed to choose one physical implementation. A multiply may become a DSP block or gates; an array may become RAM or flip-flops. Target device, timing constraints, coding pattern, tool options, and size determine the result.

2. Verilog versus SystemVerilog

SystemVerilog is a compatible extension of Verilog, not a different hardware model. It improves intent, type safety, abstraction, and verification.

Topic Verilog style SystemVerilog production style Why it matters
combinational process always @* always_comb stronger sensitivity and single-driver checks
sequential process always @(posedge clk) always_ff @(posedge clk) states intent; tools can reject illegal use
storage variable reg logic logic is a 4-state variable; clearer than historical reg
constants `define / parameter localparam, enum, package parameter scoped and typed
related signals separate ports packed struct, interface, modport fewer wiring and direction mistakes
state encoding integer parameters enum logic [...] readable waveforms and safer states
reusable types limited typedef, packages one definition across modules
verification procedural Verilog classes, constraints, assertions, coverage scalable testbench architecture

wire, reg, and logic

  • A net such as wire represents connectivity and can resolve multiple drivers.
  • A variable such as logic stores the last procedural assignment in simulation. It may represent combinational or sequential hardware depending on the process.
  • logic does not itself mean “flip-flop.” The surrounding process determines hardware.
  • Prefer logic for single-driver RTL signals. Keep a net type when true multiple-driver resolution is intended, such as an inout bus. Multiple internal drivers are usually a design error.
logic a, b, y_comb;
logic q;

always_comb y_comb = a & b;        // AND gate, no storage

always_ff @(posedge clk)
  q <= y_comb;                     // D flip-flop

Interview leverage: Say “reg never guaranteed a physical register; it was a procedural variable. In SystemVerilog I use logic, then express hardware intent with always_comb, always_latch, or always_ff.”

3. Literals, width, signedness, and four-state logic

3.1 Sized literals

The safe form is:

<width>'<signedness><base><digits>

8'hA5       // 8-bit hexadecimal A5
12'd1000    // 12-bit decimal 1000
-6'sd7      // unary minus applied to a 6-bit signed literal
4'b10x1     // contains unknown X
'0          // context-sized, fill every bit with 0
'1          // context-sized, fill every bit with 1

Use explicit widths at interfaces and in arithmetic. Unsized literals and mixed signed/unsigned operands can silently extend or truncate.

logic [7:0] a, b;
logic [8:0] sum;

assign sum = {1'b0, a} + {1'b0, b};  // explicit 9-bit unsigned addition

Width trap

logic [7:0] a, b;
logic [8:0] bad_sum, good_sum;

assign bad_sum  = a + b;                  // expression may be only 8 bits
assign good_sum = 9'(a) + 9'(b);          // sized cast; confirm tool/style support
// The concatenation form above is often clearest and most portable.

3.2 Two-state and four-state types

  • bit has only 0 and 1. It is useful in testbench algorithms and can hide X problems.
  • logic, reg, and integer vector types are four-state: 0, 1, X, and Z.
  • X means unknown/conflicting/uninitialized in simulation.
  • Z means high impedance, usually at chip I/O or a shared net.

Hardware does not contain an “X voltage.” X is a simulation abstraction. Synthesis may interpret an assigned X as a don't-care and optimize differently from simulation.

logic [3:0] status;

if (status == 4'b0001) begin       // result can be X
  ...
end

if (status === 4'b0001) begin      // exact 4-state comparison; usually testbench use
  ...
end

Use ==/!= for normal RTL decisions. Use ===/!== mainly in testbenches and assertions when X/Z must be tested explicitly. Do not “repair” an unknown control signal by casually using casex; it masks real bugs.

3.3 Signed arithmetic

Vectors are unsigned unless declared signed. A slice is unsigned even when taken from a signed vector.

logic signed [15:0] x, y;
logic signed [16:0] result;

assign result = $signed({x[15], x}) + $signed({y[15], y});

Useful casts:

$signed(expr)
$unsigned(expr)
type'(expr)       // size/type cast

Trap: Signedness and width are properties of expressions, not just destinations. Assignment into a wider destination cannot recover a carry bit that was already discarded.

3.4 Time, real, and string

timeunit and timeprecision make delay meaning local and explicit:

module tb;
  timeunit 1ns;
  timeprecision 1ps;

  initial begin
    #2.5ns;
  end
endmodule

Delays, real, shortreal, and string are generally testbench constructs. Production hardware uses counters for time, fixed-point/floating-point circuits for real-number behavior, and packed bytes or memories for text-like data.

4. Arrays, memories, structs, unions, and enums

4.1 Packed versus unpacked arrays

Dimensions before a name are packed; dimensions after a name are unpacked.

logic [7:0] byte_value;             // one packed 8-bit vector
logic [7:0] mem [0:255];            // 256 unpacked elements, each 8 bits
logic [1:0][7:0] two_bytes;         // one packed 16-bit value
logic [7:0] banks [0:3][0:255];     // 4 x 256 byte memory

Packed data behaves like one contiguous bit vector: it supports arithmetic, slicing, concatenation, and port transport. Unpacked dimensions describe collections of elements and are natural for memories.

Fixed-size arrays are synthesizable when access patterns fit the target. Dynamic arrays, queues, and associative arrays are excellent testbench containers but generally do not synthesize.

int dyn[];             // dynamic array: testbench
byte queue[$];         // queue: testbench
int score[string];     // associative array: testbench

4.2 Indexing and part-selects

logic [31:0] word;
logic [7:0] byte_i;
int unsigned i;

assign byte_i = word[i*8 +: 8];  // upward indexed part-select
// word[base -: width] selects downward

The width in an indexed part-select must be constant for synthesis; the base may be variable, typically producing a mux.

4.3 Packed structs: named wires in one bus

typedef struct packed {
  logic        valid;
  logic [2:0]  opcode;
  logic [7:0]  address;
  logic [15:0] data;
} command_t;

command_t cmd;
logic [28:0] raw;

assign raw = cmd;              // packed struct is a contiguous vector
assign cmd = command_t'(raw);  // typed cast documents intent

Hardware: exactly 29 wires or 29 flip-flops if registered. Field names do not cost area; they improve readability and prevent bit-position mistakes.

Packed field order follows declaration order from most significant toward least significant bits. Treat serialization layout as an interface contract and test it.

4.4 Unions: several views of the same bits

typedef union packed {
  logic [31:0] word;
  struct packed {
    logic [15:0] high;
    logic [15:0] low;
  } halves;
  logic [3:0][7:0] bytes;
} word_view_t;

All packed union members occupy the same 32 bits. A union normally adds no hardware; it creates alternative typed views. Members must have compatible packed sizes.

Trap: A union is not a C-style runtime tag. It does not remember which member is valid. Carry an explicit enum tag if interpretation can vary.

4.5 Enums: readable states

typedef enum logic [1:0] {
  IDLE,
  LOAD,
  RUN,
  ERROR
} state_t;

state_t state_q, state_d;

Enums synthesize as their base bits. They improve waveforms, lint, type checking, and review quality. Choose an explicit base type and width for RTL.

always_ff @(posedge clk or negedge rst_n)
  if (!rst_n) state_q <= IDLE;
  else        state_q <= state_d;

Avoid relying on enum methods such as .next() in synthesis unless your tool flow explicitly supports the pattern.

5. Combinational, sequential, and latch processes

5.1 always_comb

always_comb begin
  y = '0;               // default prevents a latch
  if (enable)
    y = a ^ b;
end

always_comb:

  • executes once at time zero in simulation;
  • infers sensitivity from read signals, including signals read in called functions;
  • communicates that written variables should not be written by another process;
  • is intended for combinational logic.

Hardware: XOR gates plus a mux controlled by enable.

5.2 Accidental latch

// Bad: y must remember its old value when enable == 0.
always_comb begin
  if (enable)
    y = data;
end

This describes storage because not every path assigns y. Use a default or complete else unless a latch is deliberately required.

always_latch begin
  if (gate_en)
    q <= d;
end

always_latch documents an intentional level-sensitive latch. Latches are valid hardware but often avoided in FPGA and synchronous ASIC styles because timing analysis and clocking are harder.

5.3 always_ff and nonblocking assignments

always_ff @(posedge clk or negedge rst_n) begin
  if (!rst_n)
    q <= '0;
  else if (enable)
    q <= d;
end

Use nonblocking <= for sequential state. Every right-hand side is evaluated using the old state and updates are scheduled together:

always_ff @(posedge clk) begin
  q1 <= d;
  q2 <= q1;
end

Hardware: two pipeline flip-flops. With blocking =, simulation ordering can make q2 appear to receive d immediately, creating a race and not matching the intended pipeline.

Use blocking = for local combinational calculations, nonblocking <= for clocked state. This guideline is stronger and safer than “blocking is sequential code, nonblocking is parallel code.”

5.4 Reset choices

  • Synchronous reset: checked only on the active clock edge; often easier for timing and FPGA mapping.
  • Asynchronous reset: acts without a clock; assertion is simple, but deassertion must be synchronized to avoid recovery/removal violations.
  • Reset control state and architectural state. Resetting every datapath register can increase area, routing, and timing cost.

6. Selection, loops, unique, and priority

6.1 if and case become decision hardware

always_comb begin
  y = d;
  case (sel)
    2'd0: y = a;
    2'd1: y = b;
    2'd2: y = c;
    default: ;        // keep y = d
  endcase
end

This normally becomes a 4-to-1 mux. A normal if / else if chain expresses ordered priority.

Avoid casex in RTL. It treats X/Z in both the expression and item as wildcards and can hide uninitialized controls. casez is appropriate only when Z/? wildcard behavior is deliberate, such as an explicitly reviewed decoder.

6.2 unique, unique0, and priority

These keywords are executable promises checked by simulation and usable by synthesis.

always_comb begin
  next = DEFAULT;
  unique case (opcode)
    OP_ADD: next = ADD_PATH;
    OP_SUB: next = SUB_PATH;
    OP_AND: next = AND_PATH;
    default: next = DEFAULT;
  endcase
end
  • unique: no more than one item may match, and one item must match unless a default handles no-match.
  • unique0: no more than one item may match; zero matches are allowed.
  • priority: the first matching item wins; simulation warns if no item matches and no final else/default exists.
always_comb begin
  grant = '0;
  priority if (req[0])      grant[0] = 1'b1;
  else if (req[1])          grant[1] = 1'b1;
  else if (req[2])          grant[2] = 1'b1;
end

Hardware: a priority encoder. unique if instead promises conditions are mutually exclusive and can permit parallel optimization.

Production rule: Never add these keywords merely to silence lint. They communicate assumptions. Add assertions for important assumptions, supply safe defaults, and check post-synthesis behavior. A false promise can produce simulation warnings and unsafe don't-care optimization.

6.3 Loops

always_comb begin
  parity = 1'b0;
  for (int i = 0; i < WIDTH; i++)
    parity ^= data[i];
end

A static loop is unrolled into hardware—in this case an XOR reduction network. It does not take WIDTH clock cycles. To reuse one operator over multiple cycles, design a counter, registers, and control FSM.

foreach is concise for arrays:

foreach (data[i])
  masked[i] = data[i] & mask[i];

break, continue, and variable loop bounds have uneven synthesis support and can imply large logic. Use static, reviewable bounds in RTL.

6.4 Generate versus procedural loop

for (genvar g = 0; g < LANES; g++) begin : gen_lane
  lane u_lane (...);
end

A generate loop creates hierarchy at elaboration. A procedural for repeats statements inside one process. Both can replicate hardware, but generate can instantiate modules, interfaces, and concurrent assertions.

7. Functions, tasks, parameters, and packages

7.1 Function as reusable combinational logic

function automatic logic [7:0] sat_add8(
  input logic [7:0] a,
  input logic [7:0] b
);
  logic [8:0] sum;
  sum = {1'b0, a} + {1'b0, b};
  return sum[8] ? 8'hFF : sum[7:0];
endfunction

Called from RTL, this function is inlined as adders and muxes wherever needed. automatic gives each call independent local storage in simulation. Synthesizable functions must avoid timing controls and dynamic behavior.

Tasks may contain multiple outputs and, in testbenches, delays/events. A timing-free task can be synthesizable but many teams reserve tasks for testbench code and use functions/modules for RTL clarity.

7.2 Parameters

module counter #(
  parameter int unsigned WIDTH = 16,
  localparam logic [WIDTH-1:0] MAX_VALUE = '1
) (...);

parameter is externally configurable. localparam cannot be overridden and is safer for internal constants. Prefer typed parameters and validate legal values at elaboration/simulation.

7.3 Packages

package protocol_pkg;
  typedef enum logic [1:0] {READ, WRITE, IDLE, ERROR} op_t;
  typedef struct packed {
    op_t         op;
    logic [15:0] addr;
    logic [31:0] data;
  } request_t;
  parameter int DATA_WIDTH = 32;
endpackage

module endpoint
  import protocol_pkg::*;
  (input request_t req);

Packages centralize types, parameters, functions, and classes. They do not create hardware themselves. Compile the package before units that import it. Prefer explicit imports in large codebases when wildcard names could collide.

8. Interfaces and modports

An interface bundles related signals and can also contain clocking blocks, assertions, tasks, and shared parameters. For RTL, use it primarily as a typed connectivity boundary.

interface stream_if #(
  parameter int DATA_W = 32
) (
  input logic clk,
  input logic rst_n
);
  logic              valid;
  logic              ready;
  logic [DATA_W-1:0] data;
  logic              last;

  modport source (
    input  clk, rst_n, ready,
    output valid, data, last
  );

  modport sink (
    input  clk, rst_n, valid, data, last,
    output ready
  );

  modport monitor (
    input clk, rst_n, valid, ready, data, last
  );
endinterface

Use the modport from the connected module's viewpoint:

module producer(stream_if.source bus);
  // producer drives valid/data/last and reads ready
endmodule

module consumer(stream_if.sink bus);
  // consumer reads valid/data/last and drives ready
endmodule

Hardware: the interface and modports add no gates by themselves. They bundle wires and enforce access directions. Logic declared inside the interface can synthesize if the tool supports it and the logic is synthesizable.

Interface versus struct

  • A packed struct is a value: one grouped collection of bits, passed or assigned as data.
  • An interface is a connectivity object: it can include signals flowing both directions and behavior shared by connected modules.
  • A modport is a view and access contract over an interface, not inheritance and not a separate instance.

Tool reality: Interfaces and modports are broadly supported in modern FPGA/ASIC flows, but restrictions vary, especially at top-level pins, across tool boundaries, and with arrays/parameterization. Use plain ports at a boundary when required by your flow.

9. Finite-state machines: a production template

typedef enum logic [1:0] {IDLE, LOAD, RUN, ERROR} state_t;
state_t state_q, state_d;

always_comb begin
  state_d = state_q;
  ready   = 1'b0;
  busy    = 1'b0;

  unique case (state_q)
    IDLE: begin
      ready = 1'b1;
      if (start) state_d = LOAD;
    end
    LOAD: begin
      busy = 1'b1;
      if (load_ok)      state_d = RUN;
      else if (timeout) state_d = ERROR;
    end
    RUN: begin
      busy = 1'b1;
      if (done) state_d = IDLE;
    end
    ERROR: begin
      if (clear_error) state_d = IDLE;
    end
    default: state_d = ERROR;
  endcase
end

always_ff @(posedge clk or negedge rst_n) begin
  if (!rst_n) state_q <= IDLE;
  else        state_q <= state_d;
end

Hardware: state flip-flops, next-state combinational logic, and output decode logic. The default gives a deterministic recovery path from illegal encodings. unique asks simulation to check overlap and helps document exclusivity.

Common FSM styles:

  • Two-process: one always_comb for next state/output, one always_ff for state. Easy to review and lint.
  • One-process: all registered logic in one always_ff. Can be compact and naturally avoids combinational latches.
  • Moore outputs depend on state; Mealy outputs depend on state and current inputs. Mealy outputs can respond within a cycle but require careful timing/glitch analysis.

10. Classes, inheritance, and polymorphism

Classes are testbench only in normal synthesis flows. They allocate simulator objects on a heap and use handles, dynamic dispatch, and garbage collection. They describe verification software, not chip structure.

10.1 Object and handle

class Packet;
  bit [7:0]  kind;
  bit [15:0] length;

  function new(bit [7:0] kind = 0);
    this.kind = kind;
  endfunction
endclass

Packet p;             // null handle, no object yet
p = new(8'hA5);       // allocate object

Assignment copies a handle, not the object:

Packet a = new();
Packet b = a;         // aliases the same object
b.kind = 8'h3C;       // a.kind also changes

Write an explicit copy() or clone() method for independent objects, and decide whether nested handles require a deep copy.

10.2 Inheritance

virtual class Transaction;
  rand bit [31:0] address;

  function new(bit [31:0] address = '0);
    this.address = address;
  endfunction

  pure virtual function string kind();
endclass

class WriteTransaction extends Transaction;
  rand bit [31:0] data;

  function new(bit [31:0] address = '0, bit [31:0] data = '0);
    super.new(address);
    this.data = data;
  endfunction

  virtual function string kind();
    return "WRITE";
  endfunction
endclass
  • extends creates an is-a relationship.
  • super accesses the base-class implementation.
  • virtual class is abstract and cannot be instantiated.
  • pure virtual declares an interface that subclasses must implement before they are concrete.
  • local hides a member within its class; protected exposes it to subclasses.

10.3 Polymorphism

Transaction tr;
WriteTransaction wr = new('h1000, 'hDEADBEEF);

tr = wr;                    // legal upcast
$display("%s", tr.kind());  // dynamic dispatch: "WRITE"

The handle type controls what members are visible at compile time. The object type controls which virtual override runs at runtime.

Downcast safely with $cast:

WriteTransaction recovered;
if (!$cast(recovered, tr))
  $fatal("Expected WriteTransaction");

Class versus struct versus interface

Construct Identity/lifetime Inheritance Typical use Synthesizable?
packed struct value bits no bus, register, packet fields yes
class heap object through handle yes transaction, driver, scoreboard normally no
interface static elaborated connectivity no class inheritance; modport views bus wiring and protocol boundary often yes, with tool limits

Interview leverage: Explain that a SystemVerilog “interface” is not the same as a Java/C# interface. Abstract class + pure virtual methods provides the OOP contract; the SystemVerilog interface construct bundles hardware/testbench connectivity.

11. Constrained random generation

Constrained random is testbench only. It explores legal stimulus space; it must be paired with checking and coverage.

class Burst;
  rand  bit [31:0] address;
  rand  int unsigned length;
  randc bit [1:0]  channel;

  constraint c_length {
    length inside {[1:16]};
  }

  constraint c_align {
    address % 4 == 0;
  }

  constraint c_boundary {
    address[11:0] + length * 4 <= 4096;
  }
endclass

Burst b = new();
assert (b.randomize()) else $fatal("Randomization failed");
  • rand chooses a legal value each successful randomization.
  • randc cycles through values before repeating, subject to constraints.
  • A constraint is declarative; do not assume textual execution order.
  • Always check the Boolean result of randomize().

Useful constraint forms

constraint c_examples {
  mode inside {READ, WRITE};          // set membership
  size dist {1 := 50, 2 := 30, 4 := 20};
  urgent -> delay == 0;               // implication
  if (kind == WRITE) strobe != '0;    // conditional
  solve kind before size;             // distribution/order guidance
}

Distribution:

  • value := weight applies the weight to that value, or to every value in a range.
  • range :/ weight distributes that weight across the whole range.

Inline constraints specialize one call:

assert (b.randomize() with {
  channel == 2;
  length inside {[8:12]};
});

Hooks:

function void pre_randomize();
  // configure modes; no randomized values yet
endfunction

function void post_randomize();
  // derive checksums or dependent non-rand fields
endfunction

Use constraint_mode() and rand_mode() sparingly; hidden mode changes make tests difficult to reproduce. Record seeds and isolate random streams for debug stability.

Trap: Random stimulus is not proof. Assertions catch temporal violations, scoreboards check end-to-end results, and coverage tells you what was exercised.

12. Processes and synchronization

12.1 fork...join

fork
  drive_requests();
  monitor_responses();
join
  • join: wait for all child processes.
  • join_any: continue when any child finishes; remaining children continue.
  • join_none: continue immediately; children run in parallel.
  • wait fork: wait for outstanding child processes.
  • disable fork: terminates descendant processes of the current process; scope carefully.

These are mainly testbench constructs. Static parallel hardware is expressed with separate always blocks and module instances.

12.2 Mailbox

mailbox #(Transaction) mbx = new(16);

// Producer
mbx.put(tr);        // blocks if bounded mailbox is full

// Consumer
mbx.get(tr);        // blocks until an item is available

A mailbox is a simulator queue for communication. Parameterize it to catch type errors. try_put, try_get, and try_peek are nonblocking.

12.3 Semaphore

semaphore bus_lock = new(1);

bus_lock.get(1);
drive_exclusive_transfer();
bus_lock.put(1);

A semaphore controls simulator access to a shared resource using keys. get() blocks; try_get() does not. Always return the same number of keys, including error paths.

12.4 Events

event packet_done;

-> packet_done;         // blocking trigger
->> packet_done;        // nonblocking trigger
@packet_done;           // wait for a future trigger
wait (packet_done.triggered); // detects trigger during current time slot

Events are synchronization pulses, not data storage. A trigger can be missed if a waiter starts later; use a mailbox, counter, or persistent state when history matters.

13. Assertions: executable design intent

Assertions are a major SystemVerilog advantage. Immediate assertions check a condition now; concurrent assertions check behavior across clock cycles.

// Immediate: procedural condition
assert (write_ptr < DEPTH)
  else $error("write_ptr out of range");

// Concurrent: valid must remain asserted and data stable while stalled
property p_hold_when_stalled;
  @(posedge clk) disable iff (!rst_n)
    valid && !ready |=> valid && $stable(data);
endproperty

assert property (p_hold_when_stalled);

Key operators:

  • |->: overlapped implication; consequent begins in the same sampled cycle.
  • |=>: non-overlapped implication; consequent begins on the next sampled cycle.
  • ##n: delay by n sampled clock events.
  • disable iff: asynchronously disables an assertion attempt for reset/invalid conditions.
  • $past, $stable, $rose, $fell: sampled-value helpers.

Assertions are active in simulation and formal verification. Some tools synthesize selected assertions into debug/checker hardware, but do not assume this by default.

Bind reusable protocol assertions without changing RTL:

bind producer stream_checker checker_i (
  .clk   (bus.clk),
  .rst_n (bus.rst_n),
  .valid (bus.valid),
  .ready (bus.ready),
  .data  (bus.data)
);

14. Worked production example: ready/valid skid register

This one-entry buffer decouples a producer from a consumer. It demonstrates an interface, modports, fixed hardware, always_comb, always_ff, and assertions.

14.1 Interface

interface rv_if #(parameter int W = 32) (
  input logic clk,
  input logic rst_n
);
  logic         valid;
  logic         ready;
  logic [W-1:0] data;

  modport source (
    input clk, rst_n, ready,
    output valid, data
  );

  modport sink (
    input clk, rst_n, valid, data,
    output ready
  );
endinterface

14.2 RTL

module rv_buffer #(
  parameter int W = 32
) (
  rv_if.sink   in,
  rv_if.source out
);
  logic         full_q, full_d;
  logic [W-1:0] data_q, data_d;

  always_comb begin
    full_d = full_q;
    data_d = data_q;

    // Can accept if empty or if the current output transfers this cycle.
    in.ready = !full_q || out.ready;

    if (in.ready) begin
      full_d = in.valid;
      if (in.valid)
        data_d = in.data;
    end

    out.valid = full_q;
    out.data  = data_q;
  end

  always_ff @(posedge in.clk or negedge in.rst_n) begin
    if (!in.rst_n) begin
      full_q <= 1'b0;
      data_q <= '0;
    end else begin
      full_q <= full_d;
      data_q <= data_d;
    end
  end

  property p_output_stable_when_stalled;
    @(posedge in.clk) disable iff (!in.rst_n)
      out.valid && !out.ready |=> out.valid && $stable(out.data);
  endproperty
  assert property (p_output_stable_when_stalled);
endmodule

14.3 Cycle behavior

Current full out.ready in.ready Result
0 0 or 1 1 accepts a new item if in.valid
1 0 0 holds current output stable
1 1 1 old item transfers; may replace it with a new item

14.4 Synthesized hardware

  • one valid flip-flop (full_q);
  • W data flip-flops (data_q);
  • combinational ready logic: !full_q || out.ready;
  • muxes feeding the valid and data registers;
  • wiring from the interface;
  • normally no hardware for the assertion.

Timing insight

This design has a combinational ready path from consumer to producer. Chaining many such stages can create a long timing path. A fully registered skid buffer breaks that path but needs additional storage/control. The correct architecture depends on throughput, latency, and timing constraints.

16. High-value interview questions

Why use nonblocking assignment in sequential logic?

It samples all right-hand sides from the pre-edge state and schedules updates together, matching parallel flip-flop behavior and avoiding process-order races.

What causes a latch?

A combinational process that does not assign an output on every path requires that output to retain its previous value. Complete the assignments or intentionally use always_latch.

Does a for loop take multiple cycles?

Not by itself. Static RTL loops are unrolled into parallel hardware. Multi-cycle reuse requires explicit state, a counter, and registers.

logic versus wire?

logic is a four-state variable suited to a single driver. A net such as wire models connectivity and supports resolution of multiple drivers. Process intent, not the word logic, determines whether storage is inferred.

Packed versus unpacked?

Packed dimensions form one contiguous vector and support arithmetic/slicing. Unpacked dimensions form a collection of separately indexed elements and naturally model memories.

Struct versus class?

A packed struct is a fixed-width value that can synthesize. A class is a dynamically allocated object accessed by handles, supports inheritance and polymorphism, and is normally testbench only.

Interface versus modport?

An interface instance bundles signals and optional behavior. A modport defines one role's allowed directions/view of that same instance.

unique versus priority?

unique promises mutual exclusivity and, normally, completeness; unique0 permits no match. priority preserves first-match order and checks that some branch matches unless a final fallback exists.

What happens to an array in synthesis?

It may become flip-flops, distributed/LUT RAM, block RAM, or an ASIC memory macro. Coding pattern, port count, reset behavior, dimensions, target, and tool directives control inference.

Are X values real hardware?

No. They represent simulation uncertainty or don't-care intent. Misusing X assignments or wildcard cases can hide bugs and create simulation/synthesis mismatches.

17. Production checklist

Combinational RTL

  • Every output is assigned on every path.
  • Defaults appear before conditional overrides.
  • Width and signedness are explicit.
  • No X-masking casex.
  • unique/priority reflects a proven invariant.
  • Combinational paths and fanout are reasonable.

Sequential RTL

  • State uses nonblocking assignments.
  • One clear owner writes each register.
  • Clock/reset behavior matches the technology plan.
  • Clock-domain crossings use an approved synchronizer, handshake, or asynchronous FIFO.
  • Reset deassertion is safe.

Types and hierarchy

  • Enums represent states/opcodes.
  • Packed structs group related one-direction data.
  • Interfaces/modports group protocols where tool flow permits.
  • Packages own shared types; duplicate magic numbers are removed.
  • Public parameters are typed and legal values are checked.

Verification

  • Every randomize() result is checked.
  • Directed corner cases complement constrained random.
  • Assertions encode protocol and state invariants.
  • Functional coverage measures intent, not just code execution.
  • Tests record seeds and are reproducible.
  • Scoreboards compare architectural results, not implementation details.

Signoff mindset

  • Clean compile and lint.
  • Reset and X-propagation reviewed.
  • Assertions pass.
  • CDC/RDC checks pass where applicable.
  • Synthesis warnings reviewed, not waived blindly.
  • Timing and area meet constraints.
  • Gate-level or equivalence strategy is defined.

18. Final memory map

  1. Bits and types define representation; width and signedness affect logic.
  2. Combinational processes become gates and muxes; incomplete assignment becomes a latch.
  3. Sequential processes become flip-flops and register-enable muxes.
  4. Static loops replicate hardware; they do not automatically consume cycles.
  5. Packed structs/enums improve names and safety without adding hardware.
  6. Interfaces/modports organize connectivity and roles.
  7. Classes provide testbench OOP; they do not synthesize.
  8. Constraints generate legal stimulus; they do not verify correctness.
  9. Mailboxes/semaphores/events coordinate simulator processes.
  10. Assertions convert assumptions and protocol rules into executable checks.

The strongest SystemVerilog code makes intent obvious to three readers at once: the engineer, the simulator/linter, and the synthesis tool.
